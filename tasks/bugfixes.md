## Bug 1: Uploaded fil viser `null%…` + uploader hænger uden feedback

**File:** [web/src/components/files/FileSystemBrowser.tsx](web/src/components/files/FileSystemBrowser.tsx)

**Root cause:** The `UploadModal` component duplicates the upload logic inline using raw `fetch` (no progress). A purpose-built `uploadFile()` utility already exists at [web/src/api/upload.ts](web/src/api/upload.ts) with XHR + `onProgress` callback — it's simply not being used.

Because `fetch` has no upload progress API, `progress` stays `null` for the entire PUT, then jumps to `100`. Line 228 renders `${progress}%…` when `isPending=true` and `progress=null` → `"null%…"`. The progress bar at lines 134–145 is hidden the whole time (`progress !== null` guard).

**Fix:** Replace the inline `mutationFn` in `UploadModal` with a call to `uploadFile()` from `upload.ts`:
```tsx
import { uploadFile } from '../../api/upload'

// mutationFn becomes:
mutationFn: async ({ file }: { file: File }) => {
  return uploadFile({
	file,
	courseId: courseId || undefined,
	folderId: currentFolderId || undefined,
	onProgress: setProgress,
  })
},
```
Remove the inline presign/confirm/fetch/XHR code. The `upload.ts` utility already handles XHR with progress, token refresh, and error handling.

Fix button label (line 228) to handle `progress = null` while awaiting presign:
```tsx
{isPending ? (progress !== null ? `${progress}%…` : 'Forbereder…') : 'Upload'}
```

## Bug 2: Kan ikke preview JPG — 400 Bad Request fra OVHCloud

**Confirmed root cause (from network tab: 400 on S3 GET):**

In [api/Skoleoverblikket.Api/Storage/S3ObjectStorage.cs](api/Skoleoverblikket.Api/Storage/S3ObjectStorage.cs) line 84:
```csharp
var encodedKey = WebUtility.UrlEncode(key.TrimStart('/'));
```
`WebUtility.UrlEncode` encodes the entire key including `/` path separators → stored key `files/uuid1/uuid2.jpg` becomes `files%2Fuuid1%2Fuuid2.jpg` in the public URL. Browser sends GET to `https://s3.../bucket/files%2F...%2F....jpg`. OVHCloud resolves the path literally and can't find the object → 400.

The upload PUT succeeds because the presigned URL uses the raw key (generated by the AWS SDK, not `BuildPublicUrl`). The mismatch is only in the public URL used for viewing.

**Fix — encode segments individually, preserve slashes:**
```csharp
private string BuildPublicUrl(string key)
{
	var encoded = string.Join("/", key.TrimStart('/').Split('/').Select(Uri.EscapeDataString));
	return $"{_options.SanitizedPublicEndpoint}/{_options.DefaultBucketName}/{encoded}";
}
```

**Note:** Existing files in the database have broken `Url` values. After fixing the code, existing records will need their URLs regenerated. Add a one-off migration endpoint or use direct DB update for existing files (ask user if needed).

## Bug 3: Kan ikke tilføje fil til timeslot i ugeplan — 409 fra API

**File:** [web/src/pages/WeekPlanPage.tsx](web/src/pages/WeekPlanPage.tsx)

**Confirmed root cause (from console error: 409 on `/ugeplan/slots/{id}/files`):**

`editingSlot` is set **once** as a state snapshot when the user clicks a slot cell (line 736: `setEditingSlot(slot)`). When `addFileMutation.onSuccess` fires `invalidateQueries`, the React Query cache updates and `weekPlanData` refreshes — but `editingSlot` state still holds the **original snapshot** with the old `files: []`.

Result: `selectedFileIds = slot.files.map(f => f.schoolFileId)` is always the stale list. The checkbox renders unchecked even after a successful attach. User tries again → 409 "Filen er allerede tilknyttet".

**Fix — track by schemaSlotId instead of full slot object:**

In `WeekPlanPage` (lines 485, 736, 821–831):
```tsx
// Replace:
const [editingSlot, setEditingSlot] = useState<WeekPlanSlotDto | null>(null)

// With:
const [editingSchemaSlotId, setEditingSchemaSlotId] = useState<string | null>(null)
const editingSlot = weekPlanData?.slots.find(s => s.schemaSlotId === editingSchemaSlotId) ?? null
```
Update click handler: `onClick={() => setEditingSchemaSlotId(slot.schemaSlotId)}`
Update close handler: `onClose={() => setEditingSchemaSlotId(null)}`

Now `editingSlot` is always the live value from the query cache — when `invalidateQueries` causes a refetch, the modal automatically gets the updated `files` list.

## Bug 4: Fortryd skema struktur virker, men opdateringen vises ikke med det samme

**File:** [web/src/pages/SkoleindstillingerPage.tsx](web/src/pages/SkoleindstillingerPage.tsx) lines 277–299

**Root cause:** `restoreMutation.onSuccess` calls both `invalidateQueries` and `setInitialized(false)` synchronously. `invalidateQueries` triggers a background refetch — the fresh data is NOT yet in the cache. The `useEffect` (line 240) fires in the same render with `initialized=false` but `template` still holding the OLD cached value. It re-syncs local state to the old data, then sets `initialized=true`. When the fresh data arrives from the server, `initialized` is already `true` so the effect skips — the UI is stuck on old values.

**Fix:** Instead of using `initialized` to gate the effect, reset local state explicitly in `onSuccess` after the query resolves, or — simpler — call `invalidateQueries` and await the new data, then sync. The cleanest approach:

```tsx
onSuccess: async () => {
  setRestoreError(null)
  // Reset initialized so the effect re-syncs when fresh data arrives
  setInitialized(false)
  // Refetch and wait for fresh data before setting success message
  await qc.refetchQueries({ queryKey: getApiV1TimeSlotTemplateQueryKey() })
  setRestoreSuccess(true)
  setTimeout(() => setRestoreSuccess(false), 4000)
},
```

Using `refetchQueries` (awaitable) instead of `invalidateQueries` (fire-and-forget) guarantees fresh data is in the cache before the effect re-runs with `initialized=false`. The effect then syncs local state from the new values.

## Bug 5: Udskriv lokale skema giver 2 sider (primarily on mobile)

**File:** [web/src/pages/PrintSchemaPage.tsx](web/src/pages/PrintSchemaPage.tsx) lines 219–228

**Root cause:** `@media print` CSS forces `.print-page { height: calc(100vh - 0px) }`. On mobile, `100vh` includes the browser chrome and is much larger relative to the A4 printable area — the container overflows onto a second blank page. This affects all three print modes (class/staff/room) since they all use the same `PrintGrid` component.

**Fix:** Remove the forced height rules and let content flow naturally:
```css
@media print {
  html, body { margin: 0; }          /* keep */
  .no-print { display: none !important; }  /* keep */
  /* DELETE: .print-page { height: calc(100vh - 0px); } */
  /* DELETE: .print-table { height: calc(100% - 72px) !important; } */
  .print-table tr { page-break-inside: avoid; }  /* ADD: prevent row splits */
}
```
